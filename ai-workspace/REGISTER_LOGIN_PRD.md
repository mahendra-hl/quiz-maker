# Teacher Registration and Login - Technical PRD

## Overview/Problem

Teachers who want to build a shared MCQ test bank currently have no way to enter the quiz maker as themselves. Without per-teacher accounts, there is no registration, no login, and no way for more than one teacher to use the app independently. This phase solves that by giving each teacher their own account — first name, last name, email, and a securely hashed password — plus a registration page, a login page, a logout action, and a simple MCQ test bank stub to land on after login. The shared test bank and MCQ authoring come later; this phase only proves that teachers can create an account, sign in, and sign out.

---

## Hypothesis

We believe that a simple email-and-password registration and login flow, with no cookies or sessions, will let multiple teachers enter the quiz maker independently and reach a shared test-bank starting point.

---

## Scope

### In Scope

- Cloudflare D1 database with a `users` table and a versioned migration
- User service that can create, update, and delete users
- Secure password hashing before any password is written to the database (never store plaintext)
- `POST /api/register` to create a new teacher account
- `POST /api/login` to authenticate by email and password hash comparison
- `POST /api/logout` so a signed-in teacher can leave the app
- Registration page and login page
- After a successful login, redirect to an MCQ test bank stub page
- Independent authentication per teacher (each teacher has their own row in `users`; login looks up that teacher's email)
- Strict TDD: behaviour tests written first (red), then implementation (green)

### Out of Scope

- MCQ question creation, editing, or listing
- Shared test bank collaboration (comments, ownership, concurrent editing)
- Quizzes, assignments, scoring, or student-facing flows
- Email verification, password reset, or "remember me"
- Role-based access control, admin users, or invitations
- OAuth, SSO, magic links, or multi-factor authentication
- JWT tokens, refresh tokens, or any token-based auth
- Route middleware that re-checks a server-side identity on every request

### Cut

- **Cookies** — Deliberately excluded. This phase must not set, read, or store cookies.
- **Session management** — Deliberately excluded. No server-side session store, no session table, no session IDs, no `Set-Cookie` headers.
- **Separate username field** — Email is the unique login identifier. A distinct username is extra surface area and is not needed for login-by-email.
- **bcrypt / native password libraries** — Native modules are not reliable on Cloudflare Workers. Use the Web Crypto API (PBKDF2) instead of adding a hashing package.
- **Client-side state library** — The project has none installed. Login success is handled by the API response plus a client redirect. Do not add Redux, Zustand, or similar.

## Technical Requirements

### Database Schema

Cloudflare D1 is not configured in this starter yet. Add a D1 database bound as `DB` in `wrangler.jsonc`, then create the schema with a Wrangler migration. Do not change the schema with ad-hoc SQL.

Suggested database name: `quiz-maker-db`. Binding name: `DB`.

```sql
CREATE TABLE users (
  id TEXT PRIMARY KEY DEFAULT (lower(hex(randomblob(16)))),
  first_name TEXT NOT NULL,
  last_name TEXT NOT NULL,
  email TEXT NOT NULL,
  password_hash TEXT NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE UNIQUE INDEX idx_users_email ON users(email);
```

Column rules:

- `id` — opaque text primary key generated by SQLite
- `first_name` / `last_name` — required, trimmed, non-empty
- `email` — required, stored lowercased, unique, used as the login identifier
- `password_hash` — required, PBKDF2 hash string (see hashing format below). Never store the plaintext password.
- No cookie, session, or token columns

### Password hashing

Use the Web Crypto API (`crypto.subtle`) so hashing works on Cloudflare Workers without a native module.

- Algorithm: PBKDF2 with SHA-256
- Iterations: 100000
- Salt: 16 random bytes per password
- Derived key: 32 bytes
- Stored format: `pbkdf2-sha256$100000$<salt-hex>$<hash-hex>`
- Verify with a timing-safe comparison
- Hashing happens inside the user service before insert or password update, so a caller cannot accidentally persist plaintext

### API Endpoints

These are Next.js App Router route handlers under `src/app/api/`. The project prefers Server Actions for form mutations, but this phase uses HTTP endpoints because registration, login, and logout must be callable as `POST` APIs. Validate every request body with Zod before use.

No endpoint may set a `Set-Cookie` header. No endpoint may read cookies. Responses must never include `password` or `password_hash`.

#### POST /api/register

Creates a new teacher account. The password is hashed before it is stored.

**Request Body:**

```json
{
  "firstName": "Jane",
  "lastName": "Doe",
  "email": "jane@school.edu",
  "password": "correct-horse-battery"
}
```

**Response:**

- Success (201):

```json
{
  "user": {
    "id": "…",
    "firstName": "Jane",
    "lastName": "Doe",
    "email": "jane@school.edu"
  }
}
```

- Error (400): validation failure (missing fields, empty name, invalid email, password shorter than 8 characters). Message describes the field error.
- Error (409): email already registered. Message: `"An account with this email already exists."`
- Error (500): unexpected server error

#### POST /api/login

Finds the user by email and compares the submitted password with the stored hash.

**Request Body:**

```json
{
  "email": "jane@school.edu",
  "password": "correct-horse-battery"
}
```

**Response:**

- Success (200): password matches; same `user` object shape as register (no password fields)
- Error (400): missing or invalid email/password shape
- Error (401): unknown email **or** password does not match. Message: `"Invalid email or password."` Use this same message for both cases so login does not reveal whether an email is registered.
- Error (500): unexpected server error

On success, the client redirects to the MCQ test bank stub. The server does not create a session and does not set a cookie.

#### POST /api/logout

Ends the current teacher's use of the app. Because this phase has no session and no cookies, the handler does not look up a user and does not clear server state. It returns success so the client can send the teacher back to the login page.

**Request Body:** none (empty JSON object is allowed)

**Response:**

- Success (200): `{ "ok": true }`
- Must not set cookies
- Error (500): unexpected server error

### User Interface Requirements

Use existing shadcn/ui components (`card`, `field`, `input`, `label`, `button`). Do not add `react-hook-form`. Theme tokens from `src/app/globals.css` only — no hard-coded hex colors.

#### Registration (/register)

- Fields: first name, last name, email, password (password input type)
- Client-side required-field hints; server validation is authoritative
- Submit calls `POST /api/register`
- On 201: send the teacher to `/login` with a short success note, or log them in by then calling login — prefer redirect to `/login` so login remains the single entry to the stub page
- On 400/409: show the error on the form via `FieldError`
- Link to `/login` for teachers who already have an account

#### Login (/login)

- Fields: email, password
- Submit calls `POST /api/login`
- On 200: redirect to `/test-bank`
- On 401: show `"Invalid email or password."`
- On 400: show the validation message
- Link to `/register` for new teachers

#### Logout

- A logout control on the MCQ test bank stub page
- Calls `POST /api/logout`, then navigates to `/login`
- Must not depend on cookies

#### MCQ test bank stub (/test-bank)

- Simple authenticated landing page after login
- Heading that this is the shared MCQ test bank
- Short copy that question authoring and collaboration are coming later
- Show the signed-in teacher's name/email from the login response (client-held for this visit only; lost on full page refresh is an accepted limitation of no sessions)
- Logout control as above

#### Home (/)

- Redirect to `/login`

## Test-Driven Development

This feature is built with strict TDD. That is a process requirement, not a suggestion.

1. For each phase, write the behaviour tests **first**.
2. Run the tests and confirm they **fail** (red) because the behaviour does not exist yet.
3. Implement only enough production code to satisfy those tests.
4. Run the tests and confirm they **pass** (green).
5. Do **not** change, remove, skip, or weaken a test to make it pass. If implementation and a test disagree, fix the implementation.
6. Tests assert observable behaviour (status codes, response bodies, database side effects, what the user sees). They do not assert on internal implementation details such as private function names.
7. Never write assertions that cannot fail (`expect(true).toBe(true)`).
8. Each test must pass in isolation. Reset mocks in `beforeEach` with `vi.clearAllMocks()`.
9. Unit tests mock D1 and `getCloudflareContext()`. They must not reach a real database, network, or model provider.
10. Colocate tests: `src/lib/services/user.ts` is tested by `src/lib/services/user.test.ts`.

Follow `.cursor/skills/testing/SKILL.md` for Vitest setup, the `@/` alias, Cloudflare mocking, and React Testing Library conventions.

## Risks and Mitigation

### Technical Risks

- **Risk**: Native password libraries fail on Workers.
- **Mitigation**: Use Web Crypto PBKDF2 only. Verify with `npm run preview`.

- **Risk**: `getCloudflareContext()` does not work under jsdom.
- **Mitigation**: Mock `@opennextjs/cloudflare` and keep D1 behind `src/lib/`.

- **Risk**: Anonymous `?` placeholders bind incorrectly in local Wrangler.
- **Mitigation**: Use numbered placeholders (`?1`, `?2`) only.

- **Risk**: Agents weaken tests to get a green suite.
- **Mitigation**: Required test cases are listed in this PRD. Do not edit them down. A failing test means the implementation is wrong.

### User Experience Risks

- **Risk**: No sessions means a refresh on `/test-bank` loses who is signed in.
- **Mitigation**: Documented limitation. Do not “fix” it with cookies in this phase. A later PRD can add real auth persistence.

- **Risk**: Generic login errors feel unhelpful.
- **Mitigation**: The generic message is intentional to avoid email enumeration. Keep it.

- **Risk**: Teachers expect MCQ tools on the stub page.
- **Mitigation**: Stub copy states that authoring and collaboration are out of scope for this phase.

## Troubleshooting Guide

Add entries here when bugs are found and fixed during implementation.

### D1 not configured
**Problem**: `env.DB` is missing or untyped.
**Cause**: Binding not added, or `cf-typegen` not run.
**Solution**: Add `d1_databases` with binding `DB` to `wrangler.jsonc`, then `npm run cf-typegen`. Do not hand-edit `cloudflare-env.d.ts`.

### Tests cannot import `@/`
**Problem**: Vitest fails to resolve `@/lib/...`.
**Cause**: `vite-tsconfig-paths` missing from `vitest.config.ts`.
**Solution**: Follow `.cursor/skills/testing/SKILL.md`.

### Password hash works in `npm run dev` but fails in preview
**Problem**: Hashing depends on a Node-only API.
**Cause**: Accidental use of Node crypto instead of Web Crypto.
**Solution**: Use `crypto.subtle` only. Confirm with `npm run preview`.

### `@vitejs/plugin-react` peer conflict on install
**Problem**: `npm install -D @vitejs/plugin-react` (latest v6) fails with `ERESOLVE` against `@babel/core@7`.
**Cause**: plugin-react v6 wants Babel 8; this repo's tree has Babel 7 (via shadcn).
**Solution**: Pin `@vitejs/plugin-react@5.1.4`.
**Code Reference**: `package.json` devDependencies

### `next build` workerd access violation on Windows
**Problem**: `npm run build` fails with `MiniflareCoreError [ERR_RUNTIME_FAILURE]` / structured exception `#0xc0000005`.
**Cause**: Local Workers runtime (`workerd`) crash on this Windows machine, not the Vitest harness. Pre-existing environment issue.
**Solution**: Update the Microsoft Visual C++ Redistributable if needed. Re-run `npm run build` locally. This is not a Phase 1 code defect.
